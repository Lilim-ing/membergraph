# 设计决策记录

## ADR-1：自研编排，不套 LangGraph

**背景**：v1 用 LangGraph 跑 `agent ⇄ tools` 循环，很合适。这个项目需要三样 v1 没有的东西。

**决策**：~150 行自研顺序编排 + 显式降级。

**理由**：
- **预算中断**：LangGraph 的 interrupt 语义面向"等人审批"，不是"钱花完了砍分支"。实现后者要绕开它的状态机。
- **黑板版本化**：需要"每次写入产生新 revision"，图框架的 state 是整体替换，不保留历史。
- **trace 与状态解耦**：事件流要独立于业务状态落盘，出问题能单独回放。

**代价**：失去 LangGraph 的流式、检查点、可视化。当前规模不需要。

**何时应该换回去**：角色数 > 10、需要并行分支汇合、需要跨进程恢复时。

## ADR-2：fake provider 是规则引擎，不是 mock

**决策**：`FakeLLM` 按角色实现确定性决策逻辑，所有数字从 payload（真实查询结果）读取。

**理由**：
- mock 返回假数据，只能测"代码不崩"，测不出"证据有没有落账本"。
- 规则引擎保留真实的数值链路，所以评测报告里的 4 条证据、2 条结论、0 个孤儿是真的。
- CI 不需要 API key，任何人 clone 下来就能跑。

**边界**：它不能证明模型归因准不准。README 和 eval 报告都写明这一点，不含糊。

## ADR-3：复购率用滚动窗口

**背景**：最初用首单 cohort（"某月首单，90 天内是否复购"），跑出 9 月复购率 0.6%，8 月 9.7%——看起来像业务崩了。

**诊断**：9 月首单的会员到 9-30 只过了 30 天，90 天观察期没走完。这是右删失（right censoring），不是业务问题。

**决策**：改为滚动 90 天口径（近 90 天 ≥2 单 / ≥1 单），cohort 口径由 `cohort_retention()` 单独提供。

**代价**：滚动窗口对短期波动不敏感，且相邻月份窗口重叠 58 天。

**取舍**：月度监控要的是可比性，不是灵敏度。评估拉新质量时用 cohort，两个口径不混用。

## ADR-4：合规用规则，不用 LLM

**决策**：引用完整性、绝对化用语、PII、折扣底线、夸大提升、频控，全部用确定性代码。

**理由**：提示词是建议，正则是控制。一个说"避免绝对化表述"的 system prompt，拦不住"保证 100% 复购"；`re.compile(r"(保证|100%|唯一)")` 可以。

**边界**：规则只能覆盖已知模式。语义层面的误导（比如用真实数字做错误归因）需要 Critic 和人工复核，规则管不了。

---

## ADR-5：预算耗尽时降级，不中断

**决策**：`BudgetExceeded` 被编排层捕获，砍分支、标注 `degraded=true` + 原因，保留已完成的部分。

**理由**：生产系统里，"给出 3 条有证据的结论 + 一句'预算不足'"比"什么都没有 + 一个异常栈"有用得多。

**代价**：降级结果可能不完整，使用者必须读 `degraded` 字段。所以 `plan.md` 顶部会显著标注，CLI 也会打印。

---

## ADR-6：不做"多 Agent 自由对话"

**决策**：角色之间不直接对话，全部通过黑板读写。

**理由**：自由对话的多 Agent 系统难以复现、难以归因、token 成本不可控。黑板 + 固定流程让每一步的输入输出都可检查。

**代价**：灵活性低。新增角色必须改编排，不能"agent 自己找人聊"。
