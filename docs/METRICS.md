# 指标口径

每个指标都在代码里写死分子、分母、过滤条件和允许维度。**口径跟着数字走**，不假设存在唯一标准。

| 指标 | 口径 | 单位 | 允许维度 |
|---|---|---|---|
| `repurchase_rate_90d` | 近 90 天购买 ≥2 次的会员 / 近 90 天购买 ≥1 次的会员 | % | 注册渠道、会员等级、城市线级、年龄段 |
| `active_rate_30d` | 期末前 30 天有购买或行为事件的会员 / 期初已注册会员 | % | 会员等级、城市线级、年龄段 |
| `aov` | 已支付 GMV / 已支付订单数 | 元 | 订单渠道、会员等级、城市线级、年龄段 |
| `return_rate` | 退货件数 / 销售件数 | % | 品类 |
| `churn_rate_180d` | 期初有购买、且期末前 180 天无购买的会员 / 期初有购买的会员 | % | 会员等级、城市线级 |
| `repeat_gmv_share` | 期内下单 ≥2 次的会员贡献 GMV / 期内总 GMV | % | 会员等级 |
| `upt` | 已支付件数 / 已支付订单数 | 件/单 | 订单渠道、品类 |
| `discount_rate` | 折扣金额 / 吊牌金额 | % | 订单渠道、会员等级 |

## 三个刻意的选择

### 1. 复购率用滚动窗口，不用首单 cohort

首单 cohort 的定义是"某月首单的会员，在 90 天内是否复购"。它有一个机械性缺陷：**最近一个月的 cohort 还没走完 90 天**，复购率必然趋近 0。用它做月度监控，会把"观察期不足"误读成"业务崩塌"。

```
2026-09 cohort：9 月首单，到 9-30 只过了 30 天 → 复购率 0.6%
2026-09 滚动窗口：7-04 ~ 9-30 有购买的会员里，≥2 单的占比 → 12.4%
```

后者月度可比。cohort 口径仍然有价值（评估拉新质量），由 `cohort_retention()` 单独提供，不混用。

### 2. 复购率的渠道维度只能用"注册渠道"

复购率的分母是**会员**，而订单渠道是**订单**属性。一个会员可以在天猫下单三次、小程序下单两次。按订单渠道切复购率，会把人拆到多个组里，分母重复计算。

所以 `repurchase_rate_90d` 的渠道维度是 `register_channel`（会员注册渠道），不是 `channel`（订单渠道）。这个限制写在 `METRIC_META` 里，Analyst 选错维度会被拒绝或回退。

### 3. 按维度查询时，整体值单独计算

```python
grouped = COMPUTERS[metric](w, start, end, dim)   # 分组
overall = COMPUTERS[metric](w, start, end, None)  # 整体
grouped["value"] = overall["value"]               # 绝不用第一行冒充整体
```

这是踩过的坑：`return_rate` 按品类查，第一行是塑身（17.98%），曾被当成整体值（实际整体 6.40%）。回归测试：`test_dimension_query_returns_overall_value_not_a_group`。

## 指标之外：分解

`decompose()` 对率型指标做 shift-share 分解：

```
总变化 = 结构效应（人群构成变化） + 行为效应（组内表现变化） + 交互项
```

支持 `aov` / `upt` / `return_rate`。**不支持的不硬套**——主指标没有分解定义时，orchestrator 直接跳过，并在 trace 里记 `decomposition_skipped`，而不是拿一个无关指标凑数。

## 数据边界

所有指标在 `data/fixtures` 的合成数据上计算。参数来源见 `docs/DATA_ASSUMPTIONS.md`，其中明确标注了哪些是"公开量级假设"、哪些是"人为设定"。**不可用于任何真实经营决策。**
